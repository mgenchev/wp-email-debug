# wp-email-debug

Interactive WP-CLI listener that intercepts outgoing WordPress email sent through the `wp_mail()` / PHPMailer pipeline and writes one readable log file per captured email.

## Requirements

- PHP 7.4+
- WP-CLI 2.8+
- WordPress with writable `mu-plugins` directory

## Installation

```bash
wp package install .
```

After publishing:

```bash
wp package install https://github.com/<owner>/<repository>.git
```

## Usage

```bash
wp email-debug
```

Optional live SMTP transport probe:

```bash
wp email-debug --probe-transport
```

The command remains open and listens for email generated by web requests, AJAX requests, WP-Cron, CLI commands, and other WordPress processes that use the same installation.

Console and log metadata use exactly three main statuses: `Successful`, `Has Issues`, and `Failed`. Filename tokens use `SUCCESSFUL`, `HAS-ISSUES`, and `FAILED`.

Example:

```text
#1  Status : Successful
    Time   : [08:54:09]
    Subject: WP Mail Test
    To     : example@example.com
    From   : WordPress <wordpress@example.test>
    Log    : ./email-debug/2026-09-17_08-54-09_SUCCESSFUL_wp-mail-test.log
```

A message with a missing attachment can be reported as:

```text
#2  Status : Has Issues
    Time   : [08:55:11]
    Subject: Invoice
    To     : example@example.com
    From   : Store <store@example.test>
    Issue  : Attachment cannot be found.
    Log    : ./email-debug/2026-09-17_08-55-11_HAS-ISSUES_invoice.log
```

Status semantics:

- `Successful`: the intercepted WordPress/PHPMailer send pipeline completed without a detected local or enabled SMTP pre-delivery issue. External delivery is still blocked by the debugger.
- `Has Issues`: the pipeline completed, but one or more detected problems could prevent real delivery or cause WordPress to send an incomplete/different message.
- `Failed`: WordPress/PHPMailer reported that the send failed.

Failed `wp_mail()` attempts are captured through WordPress' `wp_mail_failed` action. Failed entries use the `Failed` main status and receive a timestamped `FAILED` log containing the WordPress/PHPMailer error plus the available message/request context.

On shutdown the listener prints a compact session summary with `Successful`, `Has Issues`, and `Failed` counts.

## Safety model

While the listener is active, a temporary self-expiring MU runtime intercepts PHPMailer delivery. The runtime only intercepts mail while all of these are true:

- the generated session token matches;
- the WordPress installation fingerprint matches;
- the listener heartbeat is fresh;
- the session spool directory exists.

The listener updates its heartbeat once per second. If the CLI process exits unexpectedly, the temporary runtime becomes inert after a short timeout even if the file cannot be cleaned up immediately.

On normal exit, the temporary runtime, session state, and spool are removed.

The package does not attempt to decide whether a site is truly local based on its hostname. `WP_ENVIRONMENT_TYPE` is shown only as informational context and is not used as a security boundary.

## Sending issues

The debugger does not rely only on `wp_mail_failed`. WordPress catches and ignores some PHPMailer exceptions while constructing a message, so `wp_mail()` can still return success even when part of the requested email was omitted.

The runtime therefore checks both the original mail input and the configured PHPMailer transport before replacing delivery with the safe capture transport.

It can detect, where applicable:

- missing recipient addresses;
- invalid recipient addresses;
- missing or unreadable attachments;
- missing or unreadable embedded files;
- malformed custom headers;
- missing SMTP host;
- invalid SMTP port;
- SMTP authentication enabled without a username;
- SMTP authentication enabled without a password/OAuth provider;
- SMTP encryption configured without OpenSSL;
- unavailable or disabled PHP `mail()`;
- broken `sendmail_path` or Sendmail/Qmail executable;
- unsupported or unknown PHPMailer transport;
- WordPress/PHPMailer failures reported through `wp_mail_failed`.

The log explains each detected problem in practical terms. For example:

```text
ISSUES
--------------------------------------------------------------------

Issue  :    Attachment cannot be found.
File   :    D:\files\invoice.pdf
Details:    WordPress will send the email without this attachment.
```

A configuration problem can look like:

```text
ISSUES
--------------------------------------------------------------------

Issue  :    SMTP authentication has no password or OAuth provider.
Details:    The SMTP server cannot authenticate this connection with the current configuration.
```

The email status in the console distinguishes `Successful`, `Has Issues`, and `Failed` messages. The `ISSUES` block then focuses on the problem, relevant context, and practical effect.

For clean messages the section stays compact:

```text
ISSUES
--------------------------------------------------------------------

✓ No local configuration or message issues detected.
```

## Live SMTP transport probe

`--probe-transport` is opt-in because it makes a real connection to the configured SMTP server.

The probe uses the original PHPMailer SMTP configuration before interception and attempts:

1. connect;
2. TLS negotiation when configured;
3. SMTP authentication;
4. `MAIL FROM`;
5. `RCPT TO` for captured recipients;
6. `RSET` / close.

It never calls SMTP `DATA`, so the email body is not handed to the remote SMTP server and no message is intentionally delivered by the probe.

The probe uses a short timeout and can expose problems such as:

- DNS/connection failure;
- TLS failure;
- bad SMTP credentials;
- rejected envelope sender;
- rejected recipient.

Probe failures are added to the same `ISSUES` section instead of creating a separate verbose block.

The probe cannot prove that the provider would accept the later `DATA` stage, that a downstream receiving server would accept the message, or that the message would reach an inbox. Testing those stages requires a real delivery attempt, which this debugger intentionally avoids.

For PHP `mail()`, Sendmail, or custom transports, the package performs local configuration checks rather than a live SMTP probe.

## What is intercepted

The package captures email that reaches the WordPress `wp_mail()` / PHPMailer delivery pipeline.

It cannot universally intercept a plugin that sends email directly through an external provider API such as Mailgun, Amazon SES, or SendGrid without using `wp_mail()` / PHPMailer. If `pre_wp_mail` filters are detected, the CLI prints a warning because such a filter may implement an alternate delivery path.

## Logs

Captured messages are written to an `email-debug/` directory in the directory where the command was started.

Each message receives its own timestamped log file:

```text
email-debug/
├── 2026-09-17_10-14-18_SUCCESSFUL_password-reset.log
├── 2026-09-17_10-15-42_HAS-ISSUES_new-order-1842.log
└── 2026-09-17_10-16-03_FAILED_customer-note.log
```

Filenames contain only the timestamp, main status, and sanitized real email subject. Issue reasons are not appended separately. If two messages would use the same filename, a numeric suffix is added.

A log can contain:

- subject;
- From;
- To / CC / BCC / Reply-To;
- content type and charset;
- original mailer type and safe transport metadata;
- request context;
- focused `ISSUES` section;
- message body;
- alternative body when present;
- attachment names, MIME types, and sizes;
- best-effort source classification and source file;
- failure code/message and PHPMailer exception code when `wp_mail()` fails.

SMTP passwords are never written to the log.

Attachment binaries are not duplicated into logs.

The primary `EMAIL CONTENT` section keeps the standard section heading and uses additional whitespace around the captured body for easier scanning.

Message bodies are bounded to 5 MB per body part to prevent an accidental debug message from exhausting disk space.
